# Honeytoken Deployment Runbook

## 0. Локальна симуляція (dry-run) — щоб зрозуміти й відтворити потік

Перш ніж робити реальне розгортання, запусти **симуляцію кампанії**. Вона випадково
генерує decoy-значення секретів і проганяє весь потік через справжній код колектора
(`register → record_hit → export`), **нічого не публікуючи назовні**:

```bash
# з кореня репозиторію
.venv/Scripts/python.exe deploy/simulate_campaign.py
```

Створює:
- `data/campaign-manifest.csv` — `token_id, channel, secret_type, decoy_value` (що саме «садять» у канали; значення випадкові й **нефункціональні**);
- `data/ttc-simulated.csv` — TTC-датасет тієї самої форми, що й реальний (часи компрометації змодельовано з каліброваних per-channel розподілів, провенанс — `docs/ttc-sources.md`).

Далі його можна одразу подати в калькулятор (як у §7), щоб побачити весь конвеєр.

**Як перейти від симуляції до реальної кампанії:** заміни кожне decoy-значення на
справжній **Canarytoken** (сповіщає про використання, але не дає доступу), опублікуй у
канал (кроки §4), підніми webhook-колектор (§3) — і пропусти крок симуляції: датасет
заповнять реальні влучання сканерів. Решта конвеєра (§7) не змінюється.

> Параметр `--seed` робить симуляцію відтворюваною; прибери/зміни його для іншої випадкової вибірки. `--replicas N` змінює кількість токенів на пару (канал × тип).

## 1. Передумова

Перед розгортанням отримати погодження керівника на збір honeytokens-даних (§5 спеки). Збір пасивний — дані накопичуються тижнями.

Колектор для реальної кампанії працює **на сервері** (Oracle Cloud Always Free), а не на ноутбуці:
спершу виконати [`server/README.md`](server/README.md), а кроки §2 і §5 нижче — **на VM**
(`cd /opt/ttc/app`, замість `.venv/Scripts/python.exe` — `/opt/ttc/venv/bin/python`).
База кампанії існує лише там; на ноутбук її забирає `server/pull-data.sh`.

## 2. Ініціалізація сховища

Запускати **безпосередньо перед публікацією** (на VM):

```bash
cd /opt/ttc/app
/opt/ttc/venv/bin/python deploy/seed.py
```

Без аргументів скрипт реєструє повну сітку — 4 канали × 4 типи × 2 помітності × 3 репліки = 96 honeytokens — у `data/ttc.db` і виводить перелік токенів для публікації.

**Для пілоту** (менший, керований обсяг ручної публікації) звузь сітку прапорцями
`--channels`, `--secret-types`, `--visibilities`, `--replicas`:

```bash
.venv/Scripts/python.exe deploy/seed.py --channels github dotenv --secret-types aws api --replicas 1
```

Це дає 8 токенів (2 канали × 2 типи × 2 помітності × 1 репліка) — досяжний обсяг для ручного
розгортання за один прохід, і вже покриває третій вимір (помітність), не лише канал/тип.

### Вимір «помітність» (visibility): obvious / buried

Кожен honeytoken публікують у двох варіантах помітності — це перевіряє гіпотезу, що явний,
розпізнаваний патерн секрету компрометують швидше, ніж той самий секрет, вписаний непомітно:

- **`obvious`** — секрет на окремому, явно позначеному рядку з очікуваним для типу маркером
  (напр. коментар `# AWS_SECRET_ACCESS_KEY=...` у `.env`, або окремий файл `credentials.json`).
- **`buried`** — те саме значення секрету, вписане без маркера серед звичайного коду/конфігу
  (напр. як значення змінної в середині великого YAML/конфіг-файлу без коментаря чи явної назви).

Публікуй обидва варіанти в один час (щоб час доби/дня тижня не плутався з ефектом помітності)
і фіксуй `published_at` для кожного окремо.

## 3. Запуск колектора (webhook-receiver)

> Колектор приймає сповіщення Canarytokens на `POST /canarytokens` (формат
> `TokenAlertDetails` / `TokenExposedDetails` з thinkst/canarytokens) і сам розрізняє три
> види подій: `use` (токен використано), `safety_net` (використання AWS-ключа виявлено за
> звітом IAM без IP і з неточним часом, до ~4 год) і `exposed` (ключ знайшла платформа, це
> подія захисту, а не атакувальника). Старий `POST /hit` лишився для ручних тестів.
> Перевірити все локально без публікації: `.venv/Scripts/python.exe deploy/demo_webhook.py`.
>
> **Затримка сповіщень AWS-ключів.** За документацією Canarytokens сповіщення проходить через
> журнали AWS і приходить із затримкою від 2 до 30 хв. Перед кампанією виконати калібрування:
> самому викликати `aws sts get-caller-identity` з тестовим токеном у відомий момент і
> порівняти з полем `time` сповіщення. Тестовий токен (memo `token_id=calib-aws-0`) не
> зареєстрований у базі, тож колектор відповість 404, але payload усе одно потрапить у
> `raw-events.jsonl` — звідти й брати `time`. Це ж — наскрізна перевірка всього ланцюжка.

На сервері колектор уже запущено як systemd-сервіс (`server/setup.sh`) за HTTPS-адресою
`https://<домен>/canarytokens/<секрет>` — далі вона позначена як **`<WEBHOOK_URL>`**.
У продакшн-режимі відкритий лише цей шлях і `GET /healthz`; `POST /hit` вимкнено.

Локальний запуск (розробка, без секрету — відкриті `/canarytokens` і `/hit`):

```bash
.venv/Scripts/python.exe -m uvicorn collector.main:build_app --factory --port 8000
```

## 4. Публікація по каналах

Для **кожного** `token_id` зі списку `seed.py`. Для пілоту (8 токенів,
§2) знадобляться лише §4.1 (`github`) і §4.4 (`dotenv`); §4.2/§4.3
(`ci-log`/`paste`) — для повної кампанії пізніше.

### 4.1 Канал `github`

1. Перейти на [canarytokens.org](https://canarytokens.org), обрати тип токена відповідно до `secret_type`:
   - `aws` → "AWS Keys"
   - `gcp` → **окремого типу GCP у canarytokens.org немає.** Використати "Web bug / URL token":
     згенерувати JSON ключа сервісного акаунта GCP (випадковий RSA-ключ у полі `private_key`),
     а в полі `token_uri` вказати URL токена. Бібліотеки google-auth надсилають запит саме на
     `token_uri`, тож спроба скористатися ключем спрацює як HTTP-звернення до токена;
   - `db` → "DNS token": рядок підключення `postgresql://user:pass@<dns-токен>:5432/app`.
     Спроба підключитися резолвить ім'я хоста й запускає токен (src_ip тут — IP DNS-резолвера,
     а не атакувальника);
   - `api` → "Slack API token" (справжній за форматом токен Slack) або "Web bug / URL token"
     у парі `API_URL=<url-токен>` + `API_KEY=...`.
2. Webhook URL: `<WEBHOOK_URL>`; Memo: `token_id=<token_id>`; **email — теж вказати** (резервна
   копія кожного сповіщення, якщо колектор буде недоступний). Зберегти manage-посилання токена.
3. Завантажити згенерований токен (credentials файл або рядок).
4. Розмістити відповідно до `visibility` токена:
   - `obvious` — окремим рядком з явним маркером, напр. `.env`-подібний файл з коментарем
     `# AWS credentials` прямо над значенням;
   - `buried` — те саме значення без коментаря/маркера, серед звичайного коду (напр. як
     дефолтне значення аргументу в тестовому скрипті).
5. Закомітити токен у публічний GitHub-репозиторій (окремий тестовий repo).
6. Зафіксувати точний час коміту — це `published_at` для даного токена.

### 4.2 Канал `ci-log`

1. Створити Canarytoken (тип за `secret_type`), webhook URL: `<WEBHOOK_URL>`.
2. Додати токен у крок публічного CI-пайплайну (GitHub Actions / GitLab CI) так, щоб він потрапив до публічного лог-виводу.
3. Запустити pipeline; зафіксувати час публікації логу = `published_at`.

### 4.3 Канал `paste`

1. Створити Canarytoken (тип за `secret_type`), webhook URL: `<WEBHOOK_URL>`.
2. Опублікувати токен на pastebin.com (або аналогу з публічним доступом).
3. Зафіксувати час публікації пасти = `published_at`.

### 4.4 Канал `dotenv`

1. Створити Canarytoken (тип за `secret_type`), webhook URL: `<WEBHOOK_URL>`.
2. Додати токен у файл `.env` у публічному GitHub-репозиторії (у корені або підпапці):
   - `obvious` — власний `.env` з очікуваною назвою змінної (`AWS_SECRET_ACCESS_KEY=...`);
   - `buried` — та сама назва змінної серед десятків інших у великому `.env.example`,
     без виділення чи коментаря.
3. Зафіксувати час коміту файлу `.env` = `published_at`.

## 5. Уточнення `published_at` у сховищі

`seed.py` записує як `published_at` момент свого запуску. Після публікації **кожного** токена
зафіксувати точний час (на VM):

```bash
cd /opt/ttc/app
/opt/ttc/venv/bin/python deploy/set_published.py --db data/ttc.db github-aws-obvious-0 2026-10-07T14:30:00+00:00
```

Час коміту в UTC з часовою зоною дає `git log -1 --format=%cI` у тестовому репозиторії
(для пасти чи CI-логу — час зі сторінки публікації). Без цього кроку кожен TTC буде завищено.

## 6. Моніторинг і експорт даних

Сповіщення Canarytokens надходять на `<WEBHOOK_URL>` автоматично (адаптер
`collector/canarytokens.py`). Доступність стежить UptimeRobot (`server/README.md` §5).

Раз на 1–2 дні — забрати знімок на ноутбук (з кореня репозиторію):

```bash
bash deploy/server/pull-data.sh ubuntu@<PUBLIC_IP>
```

Створює `data/campaign/<час>/` з `ttc.db`, `raw-events.jsonl` і `ttc.csv`. Фінальний експорт —
з **заздалегідь зафіксованим** кінцем вікна спостереження (однаковим для всіх токенів):

```bash
.venv/Scripts/python.exe deploy/export.py --db data/campaign/<час>/ttc.db --out data/ttc.csv --now 2026-11-15T00:00:00+00:00
```

## 7. Наступні кроки після збору даних

Запустити CLI-калькулятор для аналізу:

```bash
.venv/Scripts/python.exe -m calculator.cli data/ttc.csv \
    --ttl 15 --ttl 60 --ttl 300 --ttl 3600 \
    --impact 0.8 \
    --out data/report.json
```

Результат: `data/report.json` із підігнаним розподілом, параметрами та залишковим ризиком для кожного TTL.

> Датасет тепер містить колонку `visibility` (`obvious`/`buried`), але `calculator.cli`
> поки що стратифікує лише `by_channel`/`by_secret_type` (§9 не покриває RQ про
> помітність). Додавання `by_visibility` до CLI — окрема задача моделювання (Тижні 2–3
> плану), не блокує старт збору даних.
